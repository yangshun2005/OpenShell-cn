## 摘要

用一到两段简要概述变更内容。聚焦 RFC 提出的方案及其预期达成的结果。不要在此展开完整背景、实现细节或权衡分析。

读者仅凭本节就应能理解 RFC 的意图。

## 动机

说明为什么现在需要这项变更。描述当前问题、受影响的人群，以及目前支持不佳的工作流。

提供足够上下文，让任何人都能跟上推理。通常两到五段即可。跨领域或历史包袱较重的变更可能需要更多上下文，但优先链接到相关 Issue、既往 RFC、架构文档、设计讨论、缺陷报告或外部参考，而不是重述冗长的背景材料。

值得回答的问题：

- 当前有什么是损坏的、缺失的、令人困惑的或不必要的困难？
- 哪些约束使得这件事值得通过 RFC 而非更小的 Issue 或 Pull Request 来解决？
- 如果保持当前设计不变，会发生什么？

## 非目标

列出本 RFC 有意不解决的相关问题、设计选项或实现细节。明确边界，让评审者聚焦当前决策。

当 RFC 是更大路线图的一部分时，非目标尤其有用。指出可能后续开展的工作、由其他 Issue 或 RFC 跟踪的工作，以及有意排除的需求。

大多数 RFC 用三到七个要点即可覆盖非目标，每点一句话。仅当边界容易被误读时才补充简短说明。

## 方案

这是主要设计章节：说明预期结果、API 形态、组件边界及重要不变量。

必要时将方案组织为聚焦的子章节。这通常是全文最长的一节，但大多数 RFC 应控制在两到六个子章节，每个子章节约一到四段，外加必要的图表或示例。

包含评审者需要的高价值细节：

- 公共接口，如 API、CLI 行为或配置。
- 内部边界，如 crate 职责或驱动契约。
- 用户体验与兼容性影响。
- 安全、隐私与运维约束。
- 有助于评审的图表或示例。

## 实施计划

说明项目如何从当前状态推进到提议状态。当工作跨多个组件时，优先使用具体阶段而非宽泛清单。

涵盖：

- 所需的实现、文档、测试与发布步骤。
- 变更的预期顺序及任何临时兼容层。
- 现有用户与集成如何向前迁移。
- 发布前后如何验证变更。
- RFC 能否增量实施、通过开关控制，或作为破坏性变更实施。

通常一段简短概述加三到八个要点或阶段即可。分阶段工作时，每个阶段控制在一段或紧凑的要点列表内。

## 风险

说明项目为何可能选择不采纳本方案。包括实现难度之外的代价。

考虑：

- 兼容性风险与迁移负担。
- 安全、可靠性或性能风险。
- 给 OpenShell 架构或贡献者工作流增加的复杂度。
- 新增依赖或支持义务。
- 故障模式及运维人员或用户如何诊断。

尽可能将缓解措施与剩余不确定性分开描述。

大多数 RFC 应覆盖三到六个风险，每个风险一段或一个要点。高风险方案可能需要更多细节，但应聚焦可能改变决策的风险。

## 备选方案

描述能解决同一问题的可信竞争方案，并说明为何选择本方案而非它们。包括不作为的影响。

对每个有意义的备选方案，抓住最关键的权衡，如实现复杂度或兼容性。备选方案应让最终方案更易评估，而不只是罗列被否决的想法。

大多数 RFC 应覆盖一到四个备选方案。若有多个备选方案，每个方案用一个子章节，每个子章节控制在一到三段。

## 先例

指出为本方案提供参考的现有系统或 OpenShell 既往决策。说明适用于此处的经验教训。

先例可包括上游项目、标准、本仓库的 RFC，或生产系统的运维经验。

通常两到五个参考或示例即可，每个用一段说明相关经验。

## 待决问题

列出尚未解决、需要评审者输入的设计问题与决策。随 RFC 演进保持本节更新。

每个待决问题应足够具体，便于评审者回答或转交给合适的负责人。若某个答案会实质性改变方案，请明确指出。

这通常是简短的要点列表。每个问题控制在一到两句，问题解决后即删除。
