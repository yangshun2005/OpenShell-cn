# 附录：协议扩展

> 本文是 [RFC](../README.md) 的附录。阅读前请先熟悉 RFC 正文。

**PR #2477 更新 - WebSocket 中间件：** V1 现已包含前向文本 WebSocket 操作。下方更新后的文本将这一已实现的操作与未来的 HTTP 流式传输和 WebSocket 返回路径操作区分开。

v1 契约刻意保持最小化：一个缓冲式一元 HTTP 请求 Hook 和一个前向文本 WebSocket 消息 Hook，各自带有 `allow`/`deny` 决策，以及可选转换后的内容、发现项和元数据。本附录记录 proto 不应排除的扩展，使 v1 保持精简，同时不把未来工作逼入死角。这些扩展均未承诺实现；它们用于验证 v1 形态具备前向兼容性。

## 流式传输

v1 的 `EvaluateHttpRequest` RPC 是一元的。Supervisor 缓冲有界请求体，发送一个 `HttpRequestEvaluation`，接收一个 `HttpRequestResult`。该方法刻意不包含流式传输：如果 OpenShell 后续需要分块载荷传输或增量处理，应新增独立的操作专用方法，而不是改变 `EvaluateHttpRequest` 的基数。

本节记录此类未来流式操作需要考虑的事项，以及流式传输能带来什么、不能带来什么——这一区分很容易搞错。

### 传输流式 vs 处理流式

这是两个不同概念，容易混淆：

- **传输流式** - 独立的 gRPC 操作承载多条消息（分块）。这是服务在清单中声明、由 Supervisor 协商的内容。
- **处理流式** - 中间件可在拿到完整请求体之前对部分内容采取行动。

清单字段只约束传输层，不承诺中间件能增量处理。

### 全量守卫仍需缓冲

许多守卫需要完整请求体才能工作：JSON 感知的脱敏器必须解析整个文档，PII 扫描必须看到全部内容。这类守卫即使在流式传输上，也会在内部累积所有分块，然后解析，最后在流结束时发出单个响应——决策仍在最后一个字节之后才到达。增量处理只对更窄的场景有帮助，例如字节级正则脱敏或文本流上的密钥扫描。

### 为何后续要新增流式操作

即使中间件必须缓冲完整请求体，独立的分块传输操作仍能带来两点好处：

- 它将大缓冲区从 Supervisor 移走。Supervisor 不必持有数 MB 的请求体来放入单条消息；中间件本来就需要它，也可为其分配资源，由中间件累积。
- 它避开 gRPC 的单消息大小限制（默认 4 MB）。20 MB 的推理请求无法在不提高限制的情况下放入单条消息，但可以分块。

这是保持流式操作大门敞开的最强理由，比增量解析更重要。

### 工作方式

服务会在 `Describe` 中声明分块传输支持（及限制）。支持时，Supervisor 可使用流式操作，将请求体作为消息序列发送。不支持时，继续使用一元 v1 操作；超过一元上限的请求体将采用中间件配置的 `on_error` 行为。

流式方法应使用自己的消息，而不是直接复用 `HttpRequestEvaluation`。在单个流式请求中，首条消息携带请求上下文及首批请求体字节，后续消息只携带中间件追加的更多请求体分块；流关闭标记请求结束。这样 v1 一元消息保持扁平，流式也有自己更清晰的形态。

采用 Envoy `ext_proc` 风格、对 `context` 和 `body_chunk` 使用 `oneof` 的更清晰分阶段设计，可用于未来的流式操作，因为它无需保留一元 v1 消息形态。V1 保留扁平一元请求，因为对有界请求体更简单，也避免在需求被证明之前让每个中间件都实现流式机制。

## 额外操作阶段

> **PR #2477 更新 - WebSocket 中间件：** 本节现将 `WEBSOCKET_MESSAGE/PRE_CREDENTIALS` 记录为已实现，保留 `WEBSOCKET_MESSAGE/PRE_RETURN` 作为未来预留操作。

V1 支持 `HTTP_REQUEST/PRE_CREDENTIALS` 和前向文本 `WEBSOCKET_MESSAGE/PRE_CREDENTIALS`。同一服务接口可承载更多操作，每个操作通过 `Describe` 清单声明，并通过操作专用方法调用。每个操作与阶段组合编码代理流程中的不同位置：

- `Connection/before_policy` / `HttpRequest/before_policy` - 在网络/L7 策略准入请求*之前*，用于更早分类。风险更高，因为请求内容在策略允许之前就到达服务。
- `HTTP_REQUEST/PRE_CREDENTIALS`（v1）- 策略准入请求之后、凭证注入之前。
- `HttpRequest/post_credentials` - 凭证注入之后、中继将请求写往上游之前。此 Hook 可见凭证，因此仅限内置：OpenShell 将其标记为受限 Hook，并在清单校验时拒绝任何声明它的外部注册中间件。典型用途是必须在凭证注入后运行的请求签名——例如内置的 `openshell/sigv4`，它剥离占位符签名的 AWS 头，并在请求发往上游前用 Supervisor 解析的凭证对最终请求签名。
- `HttpResponse/completed` - 上游请求完成后，发出元数据，如状态、内容长度、选定路由、选定模型及可用时的模型用量。仅通知：无请求体、无转换、无 allow/deny 裁决。它让预留式预算中间件在不引入响应体检查的情况下对派发前决策进行对账。
- `HttpResponse/before_return` - 返回路径上，上游响应后、响应到达沙箱前；检查或脱敏上游响应。
- `WEBSOCKET_MESSAGE/PRE_CREDENTIALS`（v1 前向文本）- WebSocket 升级后，对每条完整客户端文本消息、在凭证占位符重写之前。上游接触前，并发预检让每个选定阶段检查、自愿跳过或权威拒绝升级。显式拒绝优先于失败，且独立于 `on_error` 执行；OpenShell 尽力以带类型的终止原因结束每个仍可写的已打开阶段流。未绑定此绑定的附加实现不会被选中，记录覆盖率而非应用 `on_error`。二进制消息不经检查直接通过，消耗逻辑序列，并为活跃阶段记录不支持消息的覆盖率。
- `WEBSOCKET_MESSAGE/PRE_RETURN` - 对完整上游消息、在返回工作负载之前。枚举值已预留，但在返回路径检查实现前，声明它的清单会被拒绝。

策略前阶段最早运行，两个请求阶段夹住凭证注入，响应通知和响应阶段在上游调用后运行，消息阶段在解析后的中继上更晚运行。V1 仅实现上述两个凭证前组合。`HttpRequest/post_credentials` 是最近计划的请求路径后续项，因可见注入凭证而仅限内置；`HttpResponse/completed` 是独立的未来通知 Hook，用于仅元数据的调用后对账。

## 语义上下文

v1 发送完整请求，由中间件解释。未来版本可在 `HttpRequestEvaluation` 上携带解析后的语义上下文（请求类别、语义协议如 OpenAI chat completions 或 Anthropic messages、模态），并让策略针对语义范围（最新用户消息、图像部分、工具输入）。这还需要相应的清单字段，使 OpenShell 能校验策略只引用服务支持的范围和协议。

## 内容预览

ICAP 风格预览：仅发送前 N 字节，让服务在 OpenShell 缓冲前决定是否需要完整请求体。这降低最终无需处理的大请求的缓冲成本。

## 可移植功能契约与绑定

未来版本可引入命名功能契约，如 `pii-redaction`，并建立从该可移植契约到具体服务绑定的映射。策略随后可在可互换实现间保持可移植。V1 直接引用服务自有的绑定 ID，推迟这一额外间接层。

## 头部变更规则

V1 保留重复请求头及其线上顺序。外部调用前，OpenShell 省略携带凭证、路由、分帧、逐跳及 `Connection` 指定的头部。结果返回有序的 `write` 和 `remove` 变更。写入支持追加、覆盖和跳过模式，但只能针对 `x-openshell-middleware-*`。移除可针对其他可见头部，受保护类别除外。OpenShell 原子校验并应用阶段的变更，因此一个无效变更会丢弃整组变更，并遵循该配置的 `on_error` 行为。

## 中间件认证

Supervisor 中间件通过网络端点暴露 gRPC 服务。稳定传输契约要求对目标中间件服务提供机密性和认证。端点声明、身份绑定、凭证材料及轮换必须显式，而非留作部署特定约定。

阶段 1 可临时支持未认证明文 gRPC，仅当操作员在中间件条目上显式设置 `allow_insecure = true`。未选择加入的明文 `http://` 端点会被拒绝。启用例外时，OpenShell 发出醒目警告并记录可审计的配置状态，使不安全操作始终是有意且可见的。

此模式仅适用于可信本地开发、回环服务或隔离研究环境，其中中间件端点不可被不可信客户端访问。不适用于共享集群、多租户部署、公共网络，或任何被检查请求内容需要传输机密性的环境。

无中间件认证和传输安全时，网络观察者可读取被检查请求内容，活跃攻击者可冒充中间件服务，未授权客户端在中间件可达时可直接调用。由于中间件可允许、拒绝或转换出站流量，服务冒充是策略执行绕过，而不仅是可观测性风险。

阶段 2 移除明文端点支持并移除 `allow_insecure`。届时每个外部中间件连接都必须提供认证加密传输。这是有意的研究预览破坏性变更，因此阶段 1 明文配置无长期兼容保证，必须在阶段 2 前迁移。

阶段 2 的具体机制推迟。后续协议工作应选择并规定 mTLS、TLS 加显式调用方认证或等效设计，包括信任根、客户端身份、凭证交付、证书或密钥轮换、中间件身份绑定，以及 Supervisor 如何接收认证材料。

随后构建的 alpha 机制——TLS 加可选操作员提供的信任根，以及短期、精确受众的网关签名 JWT——记录在 [extension-authentication.md](extension-authentication.md)。它以 `allow_insecure_transport` 取代本节的 `allow_insecure` 设计，并缩小但未关闭阶段 2 问题：mTLS 和重叠密钥轮换仍推迟。

即使在阶段 1 明文例外期间，Hook 仍位于提供商凭证注入之前，OpenShell 不会将原始 `Authorization`、`Cookie` 或其他受保护头部转发给中间件。这在认证传输完成期间保持了内容检查与上游凭证注入的分离。
