# 附录：部署选项

> 本文是 [RFC](../README.md) 的附录。阅读前请先熟悉 RFC 内容。

本附录记录 supervisor 中间件第一版为何支持进程内内置组件加外部管理的网络服务端点，以及哪些部署模式留待后续评估。支持所有部署模式是主 RFC 明确的非目标；本文保留分析，以免决策丢失。

## 决策：内置组件与外部管理服务端点

第一版在 supervisor 内运行第一方内置组件，并将选定的外部评估路由到运维方运行、网关和 supervisor 可访问的服务。内置组件无需注册或网络传输。对于外部服务，OpenShell 只保存连接信息、请求体限制、传输设置以及各操作对应的评估/结果契约。它不打包、部署或管理服务生命周期。

理由：

- **新增基础设施最少。** 内置组件复用 supervisor 进程。外部中间件不要求 OpenShell 构建镜像打包、进程监管或新运行时。第一轮可聚焦契约、失败行为和 supervisor 集成。
- **跨计算驱动可移植。** 无论沙箱工作负载以容器、VM 还是本地进程运行，supervisor 都能访问网络端点。其他端点形态尚无通用方式与所有相关 supervisor 环境共享，因此网络端点是在各处行为一致的便携选择。
- **独立迭代。** 中间件是与另一团队的集成点。外部服务让他们按自己的节奏部署、扩缩和更新，无需与 OpenShell 发布耦合。
- **适合重计算。** 检测工作可能需要 GPU 或大量内存。外部服务可部署在资源所在处，并与沙箱集群分开扩缩。

权衡：

- 中间件是受信组件，可直接访问请求内容。作为独立网络服务，它位于 OpenShell 隔离边界之外，通常有自己的连接和凭据。主 RFC 已将信任中间件列为非目标；此部署形态依赖该假设。
- 运维方负责部署、保护和维护该服务。

## 未来选项

以下仅为方向记录，非承诺设计。本 RFC 无承诺时间表；顺序取决于初始外部服务实现、采用反馈以及沙箱间通信等支撑原语的可用性。

### 中间件运行在自己的沙箱内

将中间件打包为容器镜像，在 OpenShell 沙箱内运行，再将出站内容路由到它。中间件将继承沙箱隔离：策略强制出站、文件系统和系统调用约束，除非明确授权否则无开放互联网访问。

这是对信任问题最直接的回应。运维方不再信任中间件不泄露其检查的内容，而是像约束其他沙箱一样约束它。无网络出站的 PII 脱敏器即使镜像被攻破也无法泄露所见内容。

此选项依赖沙箱间通信（[#1049](https://github.com/NVIDIA/OpenShell/issues/1049)），目前尚不可用。落地后，这将成为不可信或第三方中间件最有吸引力的形态。

### WASM 中间件

将中间件作为 WebAssembly 模块由 supervisor 加载，与代理同进程运行。这提供强隔离、低延迟且无需运维独立服务，代价是受限运行时（库有限、无 GPU 访问）。适合正则扫描等轻量检查，不适合模型驱动的检测。

### OpenShell 管理的镜像或边车

OpenShell 自行拉取并运行中间件镜像，例如作为沙箱的边车。这改善用户体验，无需运维独立中心服务，并保持处理本地化。代价是 OpenShell 承担生命周期管理和资源问题，且单独使用时不具备上述沙箱选项的隔离优势，除非结合策略强制。
