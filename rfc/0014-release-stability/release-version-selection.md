# RFC 0014 补充 - 发布版本选择

本补充说明定义了 OpenShell 在 `0.x` 系列中，稳定版本发布后如何选择下一个预发布版本。

## 算法

1. 找到最新的稳定标签，收集目标分支上该标签之后的提交。
2. 使用 Conventional Commits 对提交分类：
   - `feat:` 请求次版本发布。
   - 带 `!` 标记或 `BREAKING CHANGE` 脚注的提交，在 `0.x` 期间请求次版本发布。
   - `fix:` 和 `deps:` 请求补丁版本发布。
   - 其他提交类型默认不请求发布。
3. 选择最高的请求升级级别。次版本优先于补丁版本。若无提交请求发布，则不创建预发布版本。
4. 递增稳定版本以获得预发布基础版本。从 `0.2.0` 起，补丁变为 `0.2.1`，次版本变为 `0.3.0`。
5. 在构建和验证新基础版本之前，创建 `-pre.1` Git 标签。若该基础版本已有预发布版本，则递增预发布编号。
6. 该基础版本在当周发布列车中视为固定。若补丁发布列车已启动，则将后续需要次版本发布的破坏性变更暂存至下周的发布列车。
7. 若预发布基础版本不大于最新稳定版本，则分支检查失败。

| 最新稳定版本 | 自稳定版本以来的提交 | 下一个预发布版本 |
| --- | --- | --- |
| `0.2.0` | `fix:` | `0.2.1-pre.1` |
| `0.2.0` | `feat:` | `0.3.0-pre.1` |
| `0.2.0` | `feat!:` | `0.3.0-pre.1` |
| `0.2.0` | 仅 `docs:` 或 `chore:` | 无预发布版本 |

Git 标签是版本的唯一事实来源；发布版本从不提交到源码。若一个提交有多个标签，优先选择稳定版本而非预发布版本，然后按语义化版本顺序选择；两者都不存在时使用提交 SHA。为选定提交打上稳定版本标签后，删除其 `-pre.N` 标签。已存储的预发布构建产物保留其来源元数据。

## Release Please

[Release Please](https://github.com/googleapis/release-please-action) 可实现提交分类和基础版本计算。在 `0.x` 期间，其清单配置应包含：

```json
{
  "bump-minor-pre-major": true,
  "bump-patch-for-minor-pre-major": false
}
```

发布工作流负责 `-pre.N` 后缀和稳定版本发布。经维护者批准，显式的 `Release-As: x.y.z` 脚注可覆盖计算结果。
