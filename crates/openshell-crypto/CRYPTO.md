# 密码学与 FIPS

OpenShell 将第一方安全敏感的密码学操作统一经由 `openshell-crypto` 处理。工作区选择 AWS-LC 作为生产后端。接口支持未来的系统 OpenSSL 后端；当前生产实现不声明符合 FIPS，严格姿态请求会失败关闭。

## 后端边界

应用代码负责协议选择、授权策略和持久化格式。后端负责密码学实现和密钥资源。`CryptoBackend` 提供随机数、增量 SHA-256 和 AES-256-GCM；`ProtocolBackend` 适配 Rustls、证书签名、密钥导入/生成和 JWT 操作。后端中立性保留了现有协议和存储数据所需的显式算法选择。

签名密钥保留后端所有权，可拒绝导出私钥。rcgen 使用这些密钥编码证书。持久化的 CA 元数据在没有密码学验证后端的情况下解析；解析不建立信任。代理通过所选 TLS 提供方检查证书/密钥匹配，并在签发的证书链中保留原始 CA 证书。

后端故障传播给调用方，不切换到其他实现。认证失败不得暴露明文或含密钥的诊断信息。添加或更换后端时，现有密文布局、摘要输入、JWT 算法和协议版本仍是兼容性约束。

## 选择与初始化

使用方 crate 继承工作区的后端选择，并在门面上启用集成特性。未使用默认后端的构建必须在使用门面前安装上下文。在构造客户端、监听器或会初始化进程级密码学提供方的依赖之前，先选择上下文。

显式上下文选择控制第一方 TLS 构建器，即使依赖已先初始化 Rustls。未显式选择时，这些构建器保留嵌入方已安装的提供方。JWT 适配器保留 jsonwebtoken 的进程全局提供方约束；该提供方无法安全替换。两种行为都不会自动重定向依赖自有的密码学操作。

## 贡献者规则与覆盖范围

新的第一方安全敏感哈希、随机数、加密、签名、验证以及 TLS/PKI/JWT 操作，统一经由 `openshell-crypto` 处理。若缺少某项操作，应扩展门面和后端实现，而不是从应用 crate 调用外部密码学实现。测试后端分发、故障处理以及任何受影响的兼容性契约。

协议和解析类型可保留在应用代码中。非安全用途和依赖自有操作需显式分类；不得声称所选后端覆盖它们，也不得静默扩大现有例外。[crate README](README.md#compatibility-and-exclusions) 记录了当前覆盖范围，包括剩余的构建产物完整性哈希、策略缓存指纹、UUID 熵、SSH 及其他依赖自有操作。对照该范围审查变更。仅凭 Cargo 特性和贡献者说明不能证明后端独占所有权。

## OpenSSL 与 FIPS 后续工作

后端能力报告描述该后端的操作。仅凭后端名称、操作成功、动态链接或干净的依赖扫描，不能确立部署合规性。生产 OpenSSL/FIPS 配置需要：

- 为每条安全敏感的密码学路径（包括依赖和所有交付进程）定义受支持的特性集和处理方式。
- 在受支持的运行时镜像中动态链接到预期的系统 OpenSSL 和提供方包，并记录版本和来源。
- 为提供方所有权、生效的提供方策略、主机运行模式和实际 TLS 配置分别提供证据。严格需求必须拒绝缺失证据或不支持的操作，不得回退。
- 对客户端、监听器和重载路径进行 TLS 策略验证，包括目标 FIPS 配置所需的 TLS 1.2 Extended Master Secret 要求。
- 检查所选构建图和交付产物，包括动态依赖、捆绑的密码学库和准确的依赖清单。所需证据不可用时必须验证失败。
- 在合格的目标环境中测试，覆盖 TLS/mTLS、JWT、持久化 CA 加载、凭据加密以及启动/算法负面用例。

这些是后续要求，不是当前后端的保证。实现细节和扩展 API 见 [crypto crate README](README.md)。
